# 0.3.2 — 2026-07-30

## Added

- **`openmeteo_get_marine` and `openmeteo_get_air_quality` gain archive access.** New `past_days` (0–92) and `start_date`/`end_date` inputs pull an archive range instead of the forecast window — the two are mutually exclusive upstream, guarded locally by new `date_range_incomplete` and `forecast_window_conflict` errors before the request is sent. Marine's real wave values go back to at least 2022; air quality's CAMS values go back to at least 2022-10-01. Both tools join the DataCanvas spillover set: new `canvas_id` input, additive `record_count`/`canvas_id`/`table_name`/`truncated` output, spilling on a wide window when `CANVAS_PROVIDER_TYPE=duckdb` and bounding the response with `truncated: true` when it isn't. `openmeteo_dataframe_describe`/`openmeteo_dataframe_query`, `src/index.ts`'s server instructions, `canvas-accessor.ts`, README, and `docs/design.md` now name both as staging tools. ([#30](https://github.com/cyanheads/open-meteo-mcp-server/issues/30))
- **`openmeteo_get_marine`'s `forecast_days` ceiling raised 7 → 8** — the endpoint accepts up to 16, but real wave values run out well before that and the boundary moves with each model run, so 8 stays inside the measured range. ([#30](https://github.com/cyanheads/open-meteo-mcp-server/issues/30))
- **Pre-call cadence validation** on `openmeteo_get_forecast`, `openmeteo_get_historical`, `openmeteo_get_marine`, and `openmeteo_get_ensemble`, via new `src/mcp-server/tools/variable-cadence.ts`. A variable Open-Meteo documents under the opposite hourly/daily bucket — `cloud_cover` in `daily_variables`, `temperature_2m_max` in `hourly_variables` — is rejected before the request with a `variable_wrong_cadence` error naming the value, its correct field, and same-cadence alternatives when the endpoint publishes any. Catalogs are per-endpoint rather than shared, since the ensemble API publishes some daily aggregates hourly too. A name in neither documented set is unknown, not invalid, and still goes upstream untouched. ([#26](https://github.com/cyanheads/open-meteo-mcp-server/issues/26))
- **`"undefined"`-unit notice** on all seven weather tools (forecast, historical, marine, air quality, ensemble, flood, climate): a variable name the upstream parser accepts but the endpoint doesn't serve returns HTTP 200 with an all-null column and the unit string `"undefined"` — now surfaced as an `enrichment.notice` naming the affected columns instead of reading as a genuine data gap. ([#26](https://github.com/cyanheads/open-meteo-mcp-server/issues/26))

## Fixed

- **A variable placed in the wrong cadence field could return a successful, all-null result** — `hourly_variables: ["temperature_2m_max"]` on the forecast endpoint answered HTTP 200 with a null column and no signal the request was malformed, the mirror image of the existing 400-on-wrong-direction case. The cadence guard and the `"undefined"`-unit notice above close both silent-failure paths. ([#26](https://github.com/cyanheads/open-meteo-mcp-server/issues/26))
